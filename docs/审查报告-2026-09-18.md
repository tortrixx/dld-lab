## 0. 结论摘要

**结论：设计骨架是扎实的，但现在还不能进代码阶段 —— 有 5 类硬伤会让模块「写出来就跑不对」。**

前四轮遍历（接口轴／一致性轴／可执行性轴／符合性轴）把**文档互相矛盾**这类问题基本清空了。
本轮换第五根轴 —— **「能不能照着写出能跑的东西」** —— 于是暴露出前四轮结构上看不见的一类问题：
**每一处单看都对，合起来跑就是错的。**

### 五类必须先解决的硬伤

| # | 问题 | 为什么是拦路虎 |
|---|---|---|
| **1** | **脉冲宽度契约缺失** | `keypad_scan` 出的是 **1ms** 宽的按键脉冲，而 `game_fsm`／`puzzle_ctrl` 全按**单周期脉冲**消费 → **一次按键被当成多次**，方向键会连跳。全项目没有一处写明「脉冲类信号多宽、由谁保证」 |
| **2** | **多重驱动（Multi-Drive）出现在 3 个模块** | `keypad_scan.r_phase`、`game_fsm.r_cnt_tens/r_cnt_ones`、`puzzle_ctrl.r_anchor` 都被**两个进程同时赋值** → Quartus 直接报错，**照抄文档骨架编译不过**。而课件 p58 专讲这条，项目对照表却标着「已规避」 |
| **3** | **顶层端口名没有唯一真值源** | 文档里标着「逐字可抄」的顶层代码用的是 `o_dot_row`／`o_seg`／`o_cat`／`o_buz`，而 `.qsf` 的 `-to` 是 `dot_row`／`seg`／… → 名字对不上时 **`port map` 静默悬空、不报错** |
| **4** | **两处「静默失效」** | ① 种子的 `or x"01"` 强制 bit0 = 1，而第二关图案选择读的**正是这一位** → 图案选择失效；② `i_round_start` 的触发时刻在文档里有**两个互斥说法** |
| **5** | **时序验证手段为零** | 50MHz 是硬约束，但工程**没有时钟约束、流程没有 TAN 步骤**，`docs/04` 的 Fmax 行没有数据来源，而 `docs/03` 已经断言「时序裕量极大」 |

## 1. 必须优先解决（CRITICAL／HIGH，已对抗性复核，共 12 条）

> 每条都经过一个独立的「**默认推翻**」复核 agent 核对过原文与行号，严重度已按复核结论修正（下表用的是**修正后**的严重度）。

#### 1. `keypad_scan-01` — r_phase 被两个进程同时赋值（多重驱动），照抄 docs/02 §4.4 的代码在 Quartus 里直接编译不过

- **严重程度**：**HIGH**　|　**类别**：可综合性　|　**置信度**：high

**证据**

```
① docs/02-模块详细设计.md:570-581（进程 1）：`signal r_phase : unsigned(1 downto 0);` … `process (clk)` / `if rst = '1' then` / `r_phase <= (others => '0');` / `elsif i_tick = '1' then` / :578 `r_phase <= r_phase + 1;              -- 自然回绕 0→1→2→3→0`。② 同文件 :610（第二个 `process (clk)`）、:639-641（进程 2）：`if r_phase = 3 then` / `-- ③ 整轮结束：用 v_round 做一次消抖判定` / :641 `r_phase     <= (others => '0');`。③ CLAUDE.md:933：`| **p58** | 多重驱动：两个以上进程写同一信号 → `Multi Drive` 错误 | 全项目**一个信号只在一个进程里写**（`docs/02` §1.2） | ✅ |`。
```

**后果**

§4.4 的两段代码块（§4.3 的“两级状态机：扫描相 + 消抖计数”）各有独立的 process … end process，实现时要放进同一个 architecture，于是 r_phase 有两个驱动源；Quartus 在 Analysis & Synthesis 报 multiple constant drivers（正是课件 p58 那条规则，项目自己记为“✅ 已规避”）——**这个模块在阶段 2 无法编译**。而 :641 是纯冗余：进程 1 的 `r_phase + 1` 在 2 位 unsigned 上本来就是 3→0 的自然回绕（注释自己写了“自然回绕”），进程 2 只是把同一个值再写一遍，对行为零贡献，却把缺陷带进来（该段还是 2026-09-18 为修 P0 缺陷“整段重写”的产物，容易被当成可信的最终代码照抄）。

**修改建议**

删掉 docs/02:641 的 `r_phase <= (others => '0');`，:639 的 `if r_phase = 3 then` 保留作“轮末”判据，注释改成“只读相计数器，不再写它”；或在 §4.4 明确写“两段必须合进同一个进程（不推荐，会把两个职责揉在一起）”。修完顺手核一遍 §4.4 内是否还有别的信号被两段同时写（当前只有 r_phase 这一处）。

> **复核结论：CONFIRMED**（修正后严重度：HIGH）
> 逐条核对，原发现的文件、行号与原文全部属实：① docs/02-模块详细设计.md:570 `signal r_phase : unsigned(1 downto 0);`、:578 `r_phase <= r_phase + 1;  -- 自然回绕 0→1→2→3→0`，在 :572-581 的 `process (clk)` 里；② 同文件 :610 是第二个 `process (clk)`，:639-641 `if r_phase = 3 then` / 注释「③ 整轮结束」/ `r_phase <= (others => '0');`；③ CLAUDE.md:933 原文 `| **p58** | 多重驱动：两个以上进程写同一信号 → \`Multi Drive\` 错误 | 全项目**一个信号只在一个进程里写**（\`docs/02\` §1.2） | ✅ |`。§4.4 把这两段都放在「关键逻辑」下，段间（:589-591）没有任何「两段须并入同一进程」的说明，两段各带 `process (clk)` 外壳，实现时自然落进同一 architecture → r_phase 双驱动。我把课件 p58 渲染出来看了（工作树里没有 PDF 副本，只有桌面那份静态课件 PDF，非过期的项目文件）：该页正是「（七）多重驱动的处理」，示例 p1 里 `count <= count + 1` / `count <= 0`，p2 里 `if (count=3) then count <= 4`，与本处「一进程自增、另一进程条件写 0」同构，页面上明写「编译器会提示 Multi Drive 错误」——所以项目自查表把它标成 ✅ 与实际代码矛盾。另按要求核了 §4.4 内是否还有别的双写：`r_round_key / r_stable / r_cnt / r_down / o_key_press`（:616-662）与 `o_kp_col`（:584，唯一并发赋值）、`o_key_code`（:669）各自都只有一个写入方，双写确实只有 r_phase 一处；:641 也确属冗余（2 位 unsigned 的 +1 本就在 3→0 回绕，:578 注释自己承认），删掉它对行为零影响。该段确系 2026-09-18 「整段重写」（:591、§4.5 :698）的产物，被当成可信终稿照抄的风险成立。故判定 CONFIRMED，仅下调严重程度。
> **更正**：事实描述无需更正，仅严重程度由 CRITICAL 下调为 HIGH。理由：若照抄，失败形态是 Quartus 在 Analysis & Synthesis 直接指名到 net 的多重驱动报错（课件 p58 与 CLAUDE.md:933 所称的 Multi Drive / multiple constant drivers），不可能漏到板上、也不可能产生「功能全错」的电路；修法只是删掉 docs/02:641 一行冗余赋值（:639 的 `if r_phase = 3 then` 保留作轮末判据），是一次编译-报错-改一行的返工，符合 HIGH「会返工」而不符合 CRITICAL「做不出来或功能全错」。建议的修法照原发现即可，另可顺带修两处：① CLAUDE.md:933 把规则出处写成「docs/02 §1.2」，但 §1.2 的 7 条硬性规则（docs/02:61-71）里并没有「一个信号只在一个进程里写」这一条，引用是空指的；② §1.1（docs/02:21）把「关键逻辑」定义为「核心代码骨架」，既然骨架按项目自己的硬约束 14 也不能含「照着拼装就编译不过」的结构，最稳的写法是在 §4.4 两段之间加一句「本段与上段的 r_phase 必须在同一进程内实现，或删去 :641 这一行（自增已含回绕）」。

#### 4. `iface-02` — 「向下移一行」的掩码公式方向反了：srl 8 表达式被当成下移，实际是上移，会把第 0 行的零片整个抹掉

- **严重程度**：**MEDIUM**　|　**类别**：逻辑正确性　|　**置信度**：high

**证据**

```
docs/01-系统设计.md:503「| 「向下移一行」 | 整个掩码**右移 8 位**：`"00000000" & m(63 downto 8)` |」；:1110-1111 §6.1「| 下移一行 | 整体右移 8 位（行与行之间本来就是连续的，安全） |」/「| 上移一行 | 整体左移 8 位 |」；同表 :499「bit 0 = 左上角」、:502「| 「向右移一列」 | 行向量**左移**：`r(6 downto 0) & '0'` |」（同一张表里左右两字用的是两种不同的约定）。对照 docs/02-模块详细设计.md:1527「v_maxr := 8 - v_h;  -- 不变量：行锚点 + 高 ≤ 8」与 :1533-1534「when "0100" => -- 下：★ 先判上限，再加 / if v_row < v_maxr then v_row := v_row + 1;」。实测：把 :503 的公式作用在 L1_P2（第 0 行第 0~2 列）上得到全 0（零片消失）；正确的下移 m(55 downto 0) & 八位零 得到第 1 行第 0~2 列。
```

**后果**

`"00000000" & m(63 downto 8)` 就是 VHDL 的 srl 8：数据朝 bit0 方向移动 = 行号减小 = 向上，不是向下。docs/01 的位序（bit0 = 左上角）与 docs/02 §10.7（下 = row+1）都证明它反了。而 §5.0 在包里声明了 shift_down_row / shift_up_row，实现者只能照这条说明写函数体 → 上/下互换；若有人按该公式平移 L1_P0/L1_P2（它们在第 0 行），会是「零片凭空消失」这种最难查的现象。§4.3 自述「这是全项目最容易出错的地方，在此单点定义」，而它本身是错的。

**修改建议**

§4.3 与 §6.1 改为：下移 = m(55 downto 0) & "00000000"（sll 8，行号递增）、上移 = "00000000" & m(63 downto 8)（srl 8）；并把措辞统一成 VHDL 运算符名（sll/srl）而不是「左移/右移」，消除二义。

**后果**
